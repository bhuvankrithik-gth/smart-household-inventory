# Known Limitations (honest)

## v2.0.0 — cloud accounts (2026-10-23) — READ FIRST; this section supersedes items 2, 3 and parts of 1 below

- **Cloud is now the real, only mode.** Firebase Auth accounts + Firestore data: sign up once, sign in on any device, same households everywhere, live sync between devices via snapshot listeners. There is no local-account mode any more; without the Firebase config (or before `firestore.rules` is published on the project) the app can show the sign-in screen but account/data calls fail — rules publishing remains the owner's one-time step (Firebase Console → Firestore → Rules → Publish).
- **Offline story (honest):** on sign-in the app mirrors the account's loaded data to AsyncStorage and re-opens on that mirror, so viewing works offline. Writes are attempted immediately; on web the Firestore SDK queues internally, and on native a failed write is stored as a serialised intent (`shi-pending-v1:{uid}`) and replayed on the next successful sync or when the app returns to the foreground. A replayed stock operation keeps its original op id, so it still applies exactly once; a replayed stock *removal* that no longer fits server stock is dropped by the negative-stock guard instead of corrupting counts.
- **Conflicts are last-write-wins.** There is no merge/CRDT layer: if two members edit the same item or list while one is offline, the later write wins. Stock counts are protected by transactions + the idempotency ledger, but plain field edits (names, notes, budget) can overwrite each other.
- **Only the selected household is live.** The app subscribes to the current household's collections; other households you belong to load when you switch to them (the household list itself is always live). The offline mirror likewise holds the most recently viewed household's data.
- **Joining a household needs a connection the first time** (the invite code must be resolved and membership written); an offline join attempt returns a clear message instead of queueing.
- **Account deletion is connection-dependent and security-gated:** it needs network access, and Firebase may require a recent login — the app surfaces that as a friendly "log out, log back in, then try again" error.
- **Migration is one-shot and device-local:** v1.x on-device data uploads only on the first cloud sign-in *on that device*, only when the cloud account has no households yet, and is marked done per account+device.
- **The showcase dataset is no longer materialised by the app** (`src/lib/showcase.ts` is a pure builder used to seed the cloud showcase account externally — shape documented in docs/ARCHITECTURE.md). Its data is real cloud data once seeded, so it behaves like any other account on any device.

1. **No APK was built in this VM.** There is no Java/Android SDK here (`java: command not found`) and EAS CLI login is the user's own credential step. The APK is produced by EAS cloud build (exact steps in README) after the user runs `eas login` + `eas init`. No EAS project exists yet — `eas init` creates/links it under Expo owner **bhuvankrithiks-team** (username bhuvan_krithik), slug `smart-household-inventory`.
2. **Firestore rules are NOT yet published.** The project was created in production mode (deny-all). Until the owner pastes `firestore.rules` in Firebase Console → Firestore → Rules → Publish (or deploys via Firebase CLI after their login), cloud reads will return permission-denied. The app detects this (`probeCloud` in `src/lib/firebase.ts`) and shows a clear "cloud rules not yet published" message on the Login screen's cloud check; **local mode is fully functional regardless**.
3. **Cloud sync:** the Firebase layer initialises Auth + Firestore and the collection map/rules are ready; the local pending-op queue is implemented, but multi-device Firestore realtime sync of every local mutation has NOT been verified against the live project (it cannot be until rules are published and two accounts exist). Treat cloud as "integration-ready, pending the rules step", local as the verified mode.
4. **OCR:** no OCR endpoint is configured (`EXPO_PUBLIC_OCR_API_URL` blank). Receipt flow works as pick-image → review/type lines → confirm-save. Point it at your own OCR service to enable automatic extraction. Receipt images are not uploaded anywhere when no endpoint is configured.
5. **Voice:** speech-recognition native plugins are not bundled (they need a development build); the Assistant supports typed natural language + confirmation, keyboard dictation, and text-to-speech examples via expo-speech.
6. **Notifications:** local notifications are generated on demand from real data when the user taps the reminder check; the OS does not guarantee exact background schedules.
7. **Add-item form:** for speed it defaults new items to category "Other household essentials" / unit "pcs" / location "Pantry" (noted in-app); richer per-item entry is a UX follow-up. All categories/units exist in the data model.
8. **Item detail consumption for recipes** records a small standard usage amount; exact quantities can be adjusted per item.
9. **Legal documents are templates**, not a lawyer's review — see docs/LEGAL.md. Grievance-contact email placeholder must be filled by the owner before public launch.
10. **iOS:** code is iOS-compatible (Expo managed workflow, no Android-only hacks) but an iOS build requires EAS + the user's Apple Developer login/TestFlight; it has not been built or tested here.
11. **Web export** is a compatibility target (laptop). The product is the native app; some native modules (camera) are phone-only features with manual fallbacks on web.

## v1.1.0 notes (2026-10-23)

- **Sample/demo data removed entirely.** The app starts empty: first open goes to sign-in/register, and a new account has no household until it creates or joins one. The on-device store key was bumped (`shi-db-v4`), so installs that carried the old sample dataset start clean instead of migrating it.
- **Account isolation hardened.** Signing in always lands on a household the signed-in account belongs to (never the previous account's); register/logout clear the current-household pointer, and a persisted pointer is re-validated on launch.
- **Full dark theme.** The app is dark-only (`userInterfaceStyle: 'dark'`, deep-navy surfaces, no light/white borders), with a dark tab bar, header and splash.
- **OTA updates enabled from this build onward.** `expo-updates` is configured (`updates.url` → the EAS project, `runtimeVersion` policy `appVersion`, production channel in `eas.json`), so future JS/UI changes can ship with `eas update` without a reinstall. Builds before v1.1.0 cannot receive these updates — v1.1.0 itself must be installed as an APK once.

## v1.2.0 notes (2026-10-23)

- **Built-in showcase (demo) account.** Signing in with `demo@shi.app` / `demo1234` materialises a complete sample household ("Sharma Household", owner Aarav Sharma) on first use — 17 items, ~30 days of rice/oil usage history so run-out predictions show real numbers, a low-stock oil, expiring tomatoes, a shopping list with a duplicate-detection trigger, two recent purchases with price history, a monthly budget of ₹8,000 in prefs, and one waste record. Nothing is seeded before that login, nothing in the UI mentions it, and it obeys the same per-account isolation as any other account (defined in `src/lib/showcase.ts`, activated in `login()` in `src/data/store.tsx`). The dataset is local-mode only and its dates are generated relative to the day it is first opened.
- **Prefs are app-global in local mode** (unchanged design): materialising the showcase account sets the shared budget preference to ₹8,000/month; other local accounts on the same device will see that budget value in Settings until they change it. Household data itself stays fully isolated per account.
